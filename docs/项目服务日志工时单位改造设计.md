# 项目服务日志工时单位改造设计

## 1. 需求背景

项目服务日志（`BizProjectScheduleLog`）当前工时字段 `workHours` 单位为**天**，但实际业务场景中用户更习惯以**小时**为单位录入工时。

同时，项目成本核算模块依赖 `workHours`（天）字段计算人力成本：
```java
// BizProjectCostDetailService.java
BigDecimal workDay = projectScheduleLogCollect.stream()
    .map(BizProjectScheduleLog::getWorkHours)
    .reduce(BigDecimal.ZERO, BigDecimal::add);
resultData.setLaborCost(workDay.multiply(perDaySalary));
```

因此需要在不影响成本核算的前提下，新增小时字段供用户录入。

---

## 2. 现状分析

### 2.1 涉及模块

| 模块 | 说明 |
|-----|------|
| 项目服务日志 | `BizProjectScheduleLog` 实体，工时单位：天 |
| 项目成本核算 | `BizProjectCostDetail` 实体，依赖 `workHours` 计算人力成本 |
| 客户服务日志 | `BizCustomerServiceLog` 实体，工时单位：天（本次不改动） |
| 工作日志 | `BizWorkLog` 实体，工时单位：天（本次不改动） |

### 2.2 数据库现状

`workHours` 字段精度：`decimal(10,1)`（1位小数）

### 2.3 精度丢失问题

如果小时转天仅保留1位小数，会导致精度丢失：

| 输入小时 | 除以8转天 | 1位小数存储 | 还原小时 | 误差 |
|---------|----------|------------|---------|------|
| 1 小时 | 0.125 天 | 0.1 天 | 0.8 小时 | **-0.2小时** |
| 3 小时 | 0.375 天 | 0.4 天 | 3.2 小时 | **+0.2小时** |
| 5 小时 | 0.625 天 | 0.6 天 | 4.8 小时 | **-0.2小时** |

**结论：1位小数无法精确存储小时转天的结果。**

---

## 3. 解决方案

### 3.1 方案设计

- 新增字段 `workHoursHour`（单位：小时），供前端录入和展示
- 保留原有字段 `workHours`（单位：天），供成本核算使用
- 后端保存时双写：`workHours = workHoursHour / 8`
- 修改 `workHours` 精度为 **3位小数**，确保小时转天不丢失精度

### 3.2 精度验证（3位小数）

| 输入小时 | 除以8转天 | 3位小数存储 | 还原小时 | 误差 |
|---------|----------|------------|---------|------|
| 1 小时 | 0.125 天 | 0.125 天 | 1.0 小时 | ✅ 0 |
| 2 小时 | 0.25 天 | 0.25 天 | 2.0 小时 | ✅ 0 |
| 3 小时 | 0.375 天 | 0.375 天 | 3.0 小时 | ✅ 0 |
| 5 小时 | 0.625 天 | 0.625 天 | 5.0 小时 | ✅ 0 |
| 7 小时 | 0.875 天 | 0.875 天 | 7.0 小时 | ✅ 0 |

**结论：3位小数可精确存储所有整数小时转天的结果。**

## 4. 数据库改动

### 4.1 修改字段精度

```sql
-- 修改 workHours 字段精度为3位小数
ALTER TABLE biz_project_schedule_log 
MODIFY COLUMN work_hours DECIMAL(10,3) COMMENT '工时(天)';
```

**说明：**
- 从 `decimal(10,1)` 改为 `decimal(10,3)`
- 历史数据自动保留，精度扩展不影响原有值
- 例如：原来存 `1.0`，修改后仍是 `1.000`

### 4.2 新增字段

```sql
-- 新增 workHoursHour 字段（单位：小时）
ALTER TABLE biz_project_schedule_log 
ADD COLUMN work_hours_hour DECIMAL(6,1) COMMENT '工时(小时)';
```

**说明：**
- `decimal(6,1)` 支持最大 9999.9 小时
- 新录入数据使用此字段

### 4.3 历史数据刷数

```sql
-- 历史数据：根据 workHours（天）反向计算 workHoursHour（小时）
UPDATE biz_project_schedule_log 
SET work_hours_hour = work_hours * 8 
WHERE work_hours IS NOT NULL AND work_hours_hour IS NULL;
```

**说明：**
- 历史数据原来以天为单位录入，乘以8转换为小时
- 例如：原来录入 `0.5` 天，刷数后 `work_hours_hour = 4.0` 小时

## 5. 后端代码改动

### 5.1 实体类改动

**文件：** `BizProjectScheduleLog.java`

```java
/**
 * 工时(天) - 用于成本核算
 */

/**
 * 工时(小时) - 用于录入和展示
 */
private BigDecimal workHoursHour;
```

### 5.2 Controller 改动

**文件：** `ProjectScheduleController.java`

**改动位置：** 保存/更新方法中，保存前计算双写

```java
// 保存前：小时转天，保留3位小数
if (projectScheduleLog.getWorkHoursHour() != null) {
    BigDecimal workHours = projectScheduleLog.getWorkHoursHour()
        .divide(new BigDecimal("8"), 3, RoundingMode.HALF_UP);
    projectScheduleLog.setWorkHours(workHours);
}
```

### 5.3 无需改动的代码

| 文件 | 说明 |
|-----|------|
| `BizWorkHoursMapper.xml` | `sum(work_hours)` 汇总，精度修改后自动适配 |
| `BizProjectCostDetailService.java` | 成本核算逻辑，继续使用 `workHours` |
| `BizProjectCostCalculateMapper.xml` | 项目成本核算SQL，无影响 |
| 工时校验逻辑（Controller） | `compareTo(BigDecimal.ONE)` 比较，3位小数不影响 |

## 8. 风险评估

| 风险点 | 说明 | 应对措施 |
|-------|------|---------|
| 精度修改影响历史数据 | 精度扩展不改变原有值 | 无风险，自动兼容 |
| 成本核算失真 | 3位小数精度足够 | 无风险，计算更精确 |
| 工时校验逻辑 | 使用 BigDecimal 比较 | 无风险，精度不影响 |
| 历史数据刷数 | 天转小时可能不精确 | 历史数据本就以天录入，刷数后展示为小时仅供参考 |
